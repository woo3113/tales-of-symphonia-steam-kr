## 0. 결론 요약

- 이 한글패치는 **런타임 그래픽 후킹 방식**이 맞습니다. 구조는
  `d3d9.dll(프록시) → korfnt\korfnt.dll(후킹 엔진) + korfnt.fnt/korfnt_0.dds(한글 비트맵 폰트)` 입니다.
- NVIDIA 전용인 이유는 코드에 "NVIDIA면 켜기" 같은 **하드 체크가 아니라**, 후킹 프레임워크가 자체 D3D9로 한글을
  그리는 경로가 **드라이버 구현 차이에 민감**해서입니다. 실제로 커뮤니티에 인텔 내장/AMD에서 "폰트 깨짐" 보고가 다수입니다.
  (사실+추정)
- **네이티브 전환은 원리적으로 가능**합니다. 이유:
  1. **번역 텍스트는 이미 데이터(TLDAT) 안에 있음** → 후킹 없이도 읽힘.
  2. 병목은 오직 **폰트**(한글 글리프)뿐이며, 게임의 폰트 시스템과 압축 포맷이 이미 파악됨.
  3. 아카이브 압축이 **TLZC = 24바이트 헤더 + raw DEFLATE** → 파이썬 zlib만으로 해제/재압축 가능.
- 다만 "완전 네이티브"는 게임 폰트뱅크 포맷 리버싱 + `TOS.exe` 정적 패치가 필요해 **작업량이 큰 프로젝트**입니다.

## 2. 동작 방식 (사실)

1. 게임 `TOS.exe`는 `d3d9.dll`에서 **`Direct3DCreate9Ex` 하나만** import → 로컬의 프록시 `d3d9.dll`이 로드됨.
2. 프록시가 시스템 d3d9로 포워딩 준비를 하고 `korfnt\korfnt.dll`을 로드.
3. `korfnt.dll`은 DllMain에서:
   - PSAPI(`EnumProcessModules`/`GetModuleBaseNameA`)로 모듈을 열거해 대상 모듈을 찾음.
   - **AOB(바이트 패턴) 스캔**으로 `TOS.exe`의 코드를 찾아 `WriteProcessMemory`로 패치.
     - korfnt 내부 시그니처 문자열: `B9 80 00 00 00 66 3B C1 73 2F 83 E0 7F 83 F8 20 77 05`
     - 이 패턴은 **실제로 TOS.exe 오프셋 0x17A81C에 존재**(확인).
   - 그 지점의 함수는 **문자코드 변환기**:
     ```
     mov ecx,0x80 / cmp ax,cx / jae L
     and eax,0x7F / cmp eax,0x20 / ja ...
     ...  ; c < 0x80 → 표[0x8AD868] 기반 매핑
     L: cmp ax,0xFF ... ; c > 0xFF → add eax, 0x8220  ; CJK는 "코드 = 유니코드 + 0x8220"
     ```
     즉 엔진은 **글리프 코드 = 유니코드 + 0x8220** 규칙으로 폰트뱅크에서 글리프를 찾습니다.
   - D3D 디바이스를 후킹해서, 게임이 그리는 폰트 텍스처를 가로채고 **자기 BMFont 아틀라스로 한글을 대체/오버레이**.
4. 텍스트는 `TLDAT`의 텍스트 뱅크에 들어 있음(R01 확인): **TXB(3.29MB, 다국어 대사)** + CSV(메뉴/아이템 문자열) 등.

부수 사실: `petromod_nvidia_profile_identifier` 문자열은 **NVIDIA 드라이버 특유의 것**(앱이 잘못된 프로파일을 요청하면 드라이버가 그 이름의 `.ogl` 파일을 찾는 알려진 현상)으로, 게임 로직이 아닙니다. 명시적 GPU 벤더 검사는 코드에서 발견되지 않았습니다.

## 3. NVIDIA 전용인 이유 (사실 + 추정)

- 코드에 `nvapi`, `nvd3dum`, `atio*`, 벤더 문자열 검사는 **없음**(미발견).
- 커뮤니티 증거:
  - "인텔 내장 글픽으로 한글 폰트 깨짐없이 플레이 하신분?" (클리앙)
  - "한패 폰트 깨짐 현상 해결 안되는데…" (다수)
  - "cpu제한 패치나 한패 둘중 하나는 포기해야" → **TSFix(60fps/버그픽스)와 `d3d9.dll` 슬롯 충돌**
- 추정 원인: 후킹 프레임워크가 게임 프레임에 한글을 직접 합성하는데, 그 텍스처 업로드/락/상태 처리 방식이
  AMD·인텔 D3D9 런타임과 어긋나 **폰트가 깨지거나 안 그려짐**. NVIDIA 드라이버에서는 우연히/관대하게 동작.
  → "사실상 NVIDIA 전용"이지, 하드코딩된 제한은 아님.

## 4. 게임 자체(네이티브) 텍스트·폰트 시스템 (사실)

- 아카이브: `FILEHEADER.TOFHDB.debug`(Shift_JIS XML: 오프셋/크기/해시/확장자) + `FILEHEADER.TOFHDB`(바이너리 인덱스) + `TLFILE.TLDAT`(데이터).
- 압축: `TLZC` 컨테이너 = **24B 헤더**(magic `TLZC` + compSize + uncompSize) + **raw DEFLATE 본문**.
  → `zlib.decompress(body, -15)` / `zlib.compressobj(...,-15)` 로 자유 변환 가능(검증: TLFNTB_D 103,480 복원 성공).
- 폰트 시스템:
  - **`TLFNTB_D`** = 폰트뱅크(`DPDF` 컨테이너). 글리프 메트릭 + **문자코드→글리프맵** 포함
    (예: `0xE1→0x21, 0xE2→0x22, 0x4E01→0x29 …`).
  - **`TOTEXB_D`** = 글리프 아틀라스 텍스처뱅크. `FontData.pac` 안에 `FONTDATA_PICxxx.TOTEXB_D` 존재(확인).
  - 문자 매핑: c>0xFF → c+0x8220 (위 2장).
- 텍스트: **TXB**(런타임 텍스트뱅크, BRXT/RSXT/NDXT/NBXT 블록, 다국어) + CSV(언어 컬럼: JP,EN,FR,IT,DE,ES).
- 확장자 구성(R01): TOANMB 27329, TOTEXB_D 15093, MXD/TOMDL 5878, PAC 4758, BIN 3262, SKP 471(스크립트), CSV 2, TXB 2, **TLFNTB_D 1**, TLCLRB 1, TLPICB_D 1.

## 5. 네이티브 전환 경로와 난이도

| 방안 | 내용 | 난이도 | 얻는 것 |
|---|---|---|---|
| **A. 완전 네이티브** | 폰트뱅크/아틀라스에 한글 글리프 추가 + char→glyph 맵에 한글 코드 등록 + `TOS.exe`의 문자 변환 함수(0x57A81C)를 **정적으로** 패치. 후킹 DLL 제거 | 높음 | 모든 GPU 동작, TSFix와 공존, 안정성 |
| **B. 정적 exe 패치 + 폰트 로더** | D3D 후킹은 버리고, 엔진 폰트 로더를 패치해 외부 한글 폰트를 읽게 함 | 중~높음 | GPU 무관, DLL 최소화 |
| **C. 후킹 재작성(벤더 무관)** | korfnt 대신 vtable 후킹 + 상태 저장/복원을 제대로 하는 자체 d3d9 래퍼 | 중 | NVIDIA 의존 제거(단, 여전히 후킹 방식) |
| **D. 참고** | 2023 리마스터판(스팀/콘솔)은 공식 한글 지원 | - | 다른 게임이라 참고만 |

### 방안 A의 구체 절차(권장)
1. 패치본 TLDAT에서 폰트뱅크/아틀라스/텍스트뱅크를 추출해 원본과 비교 → 패치가 폰트를 어떻게 우회했는지 확인.
2. `DPDF`/`TOTEXB_D` 포맷 파서 작성(해제→재직렬화 **라운드트립 바이트 동일** 검증).
3. 나눔 계열 폰트로 한글 완성형 글리프 아틀라스 생성 + 메트릭/맵 생성.
4. `TOS.exe` 0x57A81C 변환기에 한글 분기 삽입(정적 코드 케이브) — 또는 기존 CJK 매핑(`+0x8220`)을 한글 코드까지 확장.
5. `FILEHEADER.TOFHDB` 오프셋/해시 재계산 후 TLDAT 재패킹.

### 리스크 / 미확인
- 실제 **대사용 CJK 폰트뱅크 위치** 추가 확인 필요(R01의 TLFNTB_D는 "TL_FONT_TEST" 소형 → 실제 폰트는 `FontData.pac`/TXB 쪽 가능성). (미확인)
- 한글 완성형 11,172자 아틀라스 용량/글리프 슬롯 여유 문제.
- `TOS.exe` 코드 케이브 확보 및 해시/무결성 검사 유무.
- 폰트뱅크 char 맵 확장 시 인덱스 상한(예: 16비트) 제약.

# 부록: 패치본 vs 원본 비교 결과 (바이너리 인덱스 정밀 비교)

## 방법
- 패치 7z에는 debug XML이 없어, **바이너리 `FILEHEADER.TOFHDB`**를 직접 파싱해 비교.
- 레코드 레이아웃 확정(40바이트): FileSize(u64) + CompressSize(u64) + Offset(u64) + HashValue(u32) + Extension(8) + Flags(u32).
  = 헤더 40B + FileHashArray 84385*8 + FileArray 84393*40 = 4,050,840 (정확히 일치).
- 두 인덱스를 HashValue 기준으로 정렬해 비교.

## 결과
- 엔트리 수/해시 동일(84,393 / 고유 84,385) → **추가/삭제 없이 기존 파일 교체** 방식.
- 비압축 크기(=내용)가 바뀐 엔트리 **862개**:
  | 확장자 | 개수 | 비고 |
  |---|---|---|
  | BIN | 491 | 장면별 텍스트/데이터 뱅크(추정) |
  | SKP | 355 | 스크립트 |
  | TOTEXP_P | 15 | 텍스처 픽처 |
  | SO | 3 | |
  | TOANMB | 2 | |
  | TXB | 1 | 주 텍스트뱅크(대사 45,774개) |
- 재압축만 된 엔트리 39개(TOTEXP_P).

## 텍스트 인코딩
- 패치 TXB에서 **EUC-KR/CP949 한글 패턴 214,406개**(원본 2,124개).
- BIN/SKP도 동일하게 한글(CP949) 포함 → **번역 텍스트는 이미 데이터에 EUC-KR로 들어가 있음**.

## 폰트 아틀라스
- TOTEXP_P 1건: fs 1,741,956 → 16,777,348 (+15,035,392).
- 내용이 **`korfnt_0.dds`(4096x4096 DXT5)와 SHA-256 완전 동일**(2835b404...).
  → 한글 글리프 아틀라스를 **게임 데이터(텍스처)에 내장**.
- `FontData.pac` = `FONTDATA_PIC000~019.TOTEXB_D` 20장(폰트 페이지) 참조.
- 주의: 이 아카이브에서 **TOTEXP_P = 텍스처 픽처(DDS 본체)**, **TOTEXB_D = 텍스처 뱅크 디스크립터(약 50B)** 로 보임.

## 미변경(중요)
- **TLFNTB_D(폰트 메트릭/문자→글리프 맵) 미변경**, FONTDATA 디스크립터(TOTEXB_D) 미변경.
  → 글리프 매핑/메트릭은 데이터로 갱신되지 않았고, **후킹(korfnt)이 담당**.

## 네이티브 전환 관점 결론(갱신)
- 긍정: (1) 번역 텍스트가 이미 EUC-KR로 데이터에 존재, (2) 한글 아틀라스도 데이터에 존재.
- 남은 핵심: **문자코드→글리프 매핑 + 렌더링**을 후킹에서 데이터/정적 exe 패치로 옮기는 것.
  korfnt는 TOS.exe의 문자 변환 함수(0x57A81C)를 런타임 패치하고 자체적으로 한글을 그림.
- 전환안: (A) TOS.exe 정적 패치로 EUC-KR→글리프 매핑을 데이터 기반 처리 후 후킹 제거,
  (B) 폰트뱅크(TLFNTB_D)/메트릭 포맷을 리버싱해 한글 코드 매핑을 데이터에 삽입.
- 확인 필요: 폰트뱅크의 글리프 조회 기준(코드=Unicode+0x8220 인지, DBCS 코드 인지)과 메트릭 위치.

# 부록2: TOS.exe 텍스트/폰트 파이프라인 리버싱 (방안 ① 결과)

## 요약: 엔진은 Shift-JIS 인덱스 기반 자체 비트맵 폰트를 쓴다
파이프라인(확인됨):
`원본 텍스트(2바이트/char, SJIS) → 변환(0x57A810) → 글리프코드 → 글리프슬롯(0x578680) → 아틀라스 UV`
폭 계산은 0x57ACD0(변환+폭테이블) 사용. 즉 후킹(korfnt)이 건드리는 지점 = 이 파이프라인의 **변환/글리프 함수**.

## 핵심 함수 맵 (VA, 확인됨)
| VA | 역할 |
|---|---|
| **0x57A810** | **문자 변환기** (korfnt AOB 패치 대상). `c==0x5E→0x81A7`; `c<0x80→table[0x8AD868+c*2]`(전각 SJIS); `0x80≤c≤0xFF→c+0x8220`; `c>0xFF→0x831F`(고정) |
| 0x8AD868 | ASCII→전각 SJIS 맵(256×BE u16). 예: 'A'→0x8260, '0'→0x824F, ' '→0x8140 |
| **0x578680** | **글리프 슬롯 계산**. SJIS 범위로 슬롯 도출, 아틀라스 16열 그리드: `col=slot&0xF`, `row=(slot>>4)+group*12`. 0x9880+ 한자는 테이블 0x7304EA 선형검색→slot=index+0x40, group=0x13 |
| 0x7304EA | 지원 한자 SJIS 코드 리스트(u16, 0 종료) |
| 0x57ACD0 | **글자 폭**. (code&0xFF00)==0xFF00 정규화 → 변환 호출 → 폭테이블 0x8AD970/0x8ADA90 색인 |
| 0x8AD970/0x8ADA90 | 글리프 폭 테이블 |
| 0x578680 호출처(11) / 0x57A810 호출처(11) | 주 텍스트/UI 렌더 지점들(0x4609a6, 0x4d7457, 0x531fa3, 0x54bc20, 0x553957, 0x573599, 0x57625f, 0x5762ee ...) |
| 0x57A880 | 텍스트 레이아웃 루프(줄바꿈/자간). 호출처 7(0x55427e, 0x55b796 ...) |

## 폰트 리소스 서브시스템 (확인됨)
| VA | 역할 |
|---|---|
| 0x612DA0 | TL 리소스 로더: `TLFNTB_D`(폰트뱅크), `TLPICB_D`, `TLCLRB` 등록 |
| 0x87CA44/54/64 | 기본 폰트명: `TL_FONT_COLOR`, `TL_FONT_PICTURE`, `TL_FONT_SYSTEM` |
| 0x87CA74/A88/B10/B18/B1C/B2C/B34 | 폰트 태그명: Body, Dx, Picture, id, Ruby, text, Replace, Color |
| 0x614120 | 폰트뱅크 생성자(기본 폰트 슬롯, scale=1.0) |
| 0x614210 | 폰트뱅크 접근자 |
| 0x6120C0 | 폰트 로드 |
| 폰트뱅크 파일(TLFNTB_D, DPDF) | 패치본/원본 모두 미변경 (글리프 매핑은 런타임 후킹이 담당) |

## 네이티브 패치 청사진 (방안 A: 정적 exe 패치)
핵심: 후킹이 하는 일(한글 코드→글리프)을 **정적 코드 패치 + 폰트 아틀라스 확장**으로 대체.
1. **변환기(0x57A810) 패치**: EUC-KR 리드/트레일(0xB0A1..0xC8FE)을 감지해, 한글 전용 글리프 코드 대역(예: 신규 SJIS 대역 또는 가상 코드)으로 매핑. (현재 c>0xFF는 0x831F 고정 → 여기서 한글 분기 추가)
2. **글리프 슬롯(0x578680) 패치**: 위 한글 코드 → 아틀라스의 **여유 슬롯 대역**으로 인덱싱(그룹/행 계산 포함).
3. **폭(0x57ACD0) 패치**: 한글은 고정 전각 폭(예: 24px) 반환.
4. **아틀라스**: 4096×4096 DXT5(korfnt_0.dds, 이미 확보)를 해당 텍스처 슬롯에 배치 → 한글 글리프 포함.
   - 주의: 폰트 아틀라스의 실제 페이지/치수(16열 그리드, 그룹당 행 수)와 여유 슬롯 확인 필요.
5. (선택) 한자 리스트(0x7304EA) 확장 대신 **신규 코드 대역**을 쓰면 코드케이브/테이블 확장 최소화.

## 이 방식의 장점/리스크
- 장점: 모든 GPU 동작, TSFix(60fps) 공존, 후킹 DLL 제거 → 원래 목표 달성.
- 리스크/미확인:
  - 아틀라스 레이아웃(16열/그룹 12행)과 여유 슬롯, 페이지 수(20) 확정 필요.
  - 2바이트/char 전제: 한글도 2바이트(EUC-KR)라 길이 정합 OK. 단 텍스트가 UCS-2인지 SJIS 바이트열인지 최종 확인 필요.
  - 여러 렌더 경로(0x578680/0x57A810 호출 11곳)가 모두 같은 규칙을 쓰는지 확인.
  - 코드케이브 확보와 exe 무결성(서명/체크섬) 여부.

## 결론
- 후킹이 하는 일의 정체를 확인: **변환기(0x57A810) + 글리프슬롯(0x578680)** 을 런타임 패치.
- 네이티브화는 **이 두 함수(+폭 함수)를 정적으로 패치**하면 됨 → 후킹 DLL 불필요. 폰트 아틀라스는 이미 데이터에 있음.
- 다음 작업: (a) 아틀라스 슬롯 여유/레이아웃 확정, (b) 변환기/글리프 함수용 코드케이브 패치 작성, (c) 텍스트가 EUC-KR 바이트열인지/2바이트인지 최종 확인.

# 부록3: 한글 폰트 아틀라스 생성 (방안 ③-a 결과)

## 엔진 폰트 규격 (확인됨)
- 셀 48x48px, 16열 x 12행/페이지 = 192글리프/페이지, 페이지당 768x576 DXT5 mips=3 (580736B).
- UV = (col*48, row*48); 페이지 선택 = group, 행 = (slot>>4) + group*12.
- 폰트타입 4종 x 20페이지: FONTDATA_A/B/C ..._PIC000~019 + PAL_FONTB0(768x1728) + SYSTEM_PIC000~008 + NUMERALFONTTEX + TL_FONT_TEST.
- 패치는 폰트 텍스처 중 PAL_FONTB0 하나만 4096^2 한글 아틀라스로 교체(나머지 페이지 미변경).

## 생성 결과 (work\kf13\page_00..12.dds)
- KS X 1001 한글 전체 2,350자 + ASCII 95자 = 2,445글리프 -> 13페이지.
- 규격: 768x576 DXT5 mips=3, 580736B (원본 페이지와 동일 포맷).
- 폰트: malgun.ttf(맑은 고딕) 40px. (원 패치는 나눔바른고딕 -> 교체 가능)
- 알파 = 글리프 커버리지 (RGB=white).
- 참고: Malgun에서 백슬래시가 '₩'로 렌더되는 로케일 특성(수정 필요, 사소).

## 매핑 공식 (테이블 불필요)
- 한글: glyph = 0x4000 + ((b0-0xB0)*94 + (b1-0xA1))   (EUC-KR 0xB0A1..0xC8FE)
- ASCII: glyph = 0x4000 + 2350 + (c-0x20)             (0x20..0x7E)

## 방안 ③-b: 세 함수 정적 패치 설계
1) 변환기 0x57A810:
   - c in 0x20..0x7E  -> return 0x4000+2350+(c-0x20)
   - c in 0xB0A1..0xC8FE -> return 0x4000+((hi-0xB0)*94+(lo-0xA1))
   - 그 외 -> 원래 동작(전각표/0x8220)
2) 슬롯함수 0x578680:
   - ax in 0x4000..0x4000+2445 -> slot=ax-0x4000; eax(group)=slot/192; ecx=slot%192; jmp 0x578737
3) 폭함수 0x57ACD0:
   - ax in 0x4000.. -> 한글/ASCII 전각 폭(48) 반환
- 코드케이브 필요(신규 로직 + 원본 호출 보존). 배치는 폰트타입 페이지 13장 교체.
